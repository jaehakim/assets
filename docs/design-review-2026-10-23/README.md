# AssetFlow 디자인·사용성 재점검

점검일: 2026-10-23

## 결론

관리 콘솔의 기본 구조와 공통 그리드는 갖추었지만, 운영 판단에 필요한 상태 신뢰성, 가독성, 작업 연결과 모바일 내비게이션을 우선 개선해야 한다. 장식적 관제 문구와 작은 글씨가 많고, 실제 조치로 이어지는 흐름은 약하다. 기존의 밀도 높은 업무용 콘솔 방향은 유지하되, 상태·검색·탐색을 먼저 바로잡는 것이 적절하다.

## 범위와 검증 한계

- Docker 18080, K3s 30080, 개발 서버 18082에서 로그인 화면을 브라우저로 확인했다.
- 로그인 이후에는 **개발 서버와 브라우저 내부 가상 API 응답**으로 대시보드, 자산 관리, SW 컴플라이언스, Agent 배포, 업데이트 이력, 시스템 가이드, 서버 모니터링, 점검 일지를 열었다. 운영 계정으로 인증하거나 운영 데이터를 변경하지 않았다.
- 1440, 768, 390px 화면 폭에서 대시보드를 캡처했다. 빈 데이터 및 모니터링 API 오류 상태를 확인했다.
- 자산 상세/생애주기, 입력·저장, Windows 트레이는 소스 검토 범위다. 실제 장비의 데이터, Windows DPI, 대규모 데이터, 업로드와 저장 성공 흐름은 실행 검증하지 않았다.
- 로컬에 미커밋 변경이 있으므로 인증 후 개발 화면의 모든 문제를 현재 배포본과 동일하다고 단정하지 않는다.
- 아래 우선순위는 이번 제품 점검의 판단이며 접근성 인증이나 정량 사용성 평가 결과가 아니다.

## 화면별 설계 방향

- **로그인:** 현재 브랜드와 진한 남색은 유지한다. 입력 영역의 가독성을 높이고 사실 확인되지 않은 정상·보호 상태 문구를 정리한다.
- **대시보드:** 상단에 데이터 기준 시각과 수집 상태, 그 아래 핵심 수치와 조치 필요 목록을 둔다. 같은 경고를 여러 카드에서 반복하는 비중을 줄인다. 빈 데이터에는 Agent 설치 안내를 제공한다.
- **자산 목록:** 검색·필터·결과 수·내보내기를 하나의 도구 영역에 묶는다. 기본 열은 장비, 사용자/부서, 연결 상태, 마지막 통신, 조치 필요 상태로 시작하고 나머지는 열 설정에서 선택한다. 현재 CSV 링크는 검색 조건을 전달하지 않으므로 전체 내보내기인지 명시하거나 현재 조건과 일치시킨다.
- **상세/생애주기:** 요약, 하드웨어, 소프트웨어, 보안, 관리 이력을 탭으로 구분한다. 읽기 영역과 편집 영역을 분리하고 미저장 변경을 닫을 때 알려준다.
- **컴플라이언스:** 탐지 장비와 조치 판단을 앞에 두고 기준 등록은 별도 패널로 분리한다. 제품 설치와 위반 확정을 구분하는 현재 설명은 유지한다.
- **Agent 배포/이력:** 파일·버전·변경내역을 등록 전에 요약하고 등록 진행/결과를 분명하게 표시한다. 이력과 현재 배포 버전의 연결을 강화한다.
- **모니터링/점검:** 정상·주의·장애·미확인·갱신 실패를 일관되게 사용한다. 오류와 실제 장애를 구분하고 마지막 성공 수집 시각을 항상 표시한다.
- **Windows 트레이:** 소스에는 색뿐 아니라 상태명과 마지막 통신 시각이 있어 유지할 가치가 있다. 웹과 상태 용어를 맞추고 긴 오류는 요약+상세 보기로 정리한다. 실제 Windows 100/150/200% 배율에서 아이콘/문구 확인은 별도 필요하다.

## 권장 공통 규칙 및 완료 확인

1. 타이포그래피: 페이지 제목 22–24px, 섹션 제목 16px, 본문 14px, 표 13px, 보조 12px을 출발점으로 실제 화면에서 조정한다.
2. 간격: 4/8/12/16/24px 체계, 일반 버튼 36px, 모바일 주요 조작 44px을 설계 목표로 한다.
3. 상태: 색+텍스트+필요한 아이콘을 함께 사용하며 미측정/오래된 데이터는 중립 색으로 분리한다.
4. 표: 검색·필터·정렬·결과 수·빈 상태·오류·페이지 이동의 규칙을 모든 목록에 적용한다.
5. 검증: 1440/1280/768/390px, 키보드만 사용, 200% 확대, 빈/1개/다수 데이터, 긴 장비명·부서명, API 실패·느린 응답·세션 만료를 확인한다.
6. 배포 전 확인: 개발 소스와 배포 이미지 차이를 식별하고 동일 데이터 조건으로 변경 전후 캡처를 비교한다.

## 증거 파일

- `login-18080.png`, `login-30080.png`, `login-18082.png`: 실제 비인증 로그인 화면
- `dashboard-empty-desktop.png`, `dashboard-1440.png`, `dashboard-768.png`, `dashboard-390.png`: 가상 빈 데이터 대시보드
- `view-*.png`: 개발 서버의 각 메뉴와 가상 응답 화면
- `observations.json`: 포트별 제목, 메뉴 진입 결과, 화면 폭별 DOM 측정

스크린샷의 0건은 운영 자산 수가 아니다. 모바일 캡처는 여러 탭을 먼저 연 상태이므로 처음 접속했을 때의 메뉴 접근성은 소스의 초기 탭 상태와 함께 판단했다. 앱의 전환 애니메이션이 있어 observations.json의 mainLeft 순간값은 최종 레이아웃 치수로 사용하지 않았다.

이번 작업에서는 점검 문서와 증거 이미지만 추가했으며 애플리케이션 코드나 배포 상태는 변경하지 않았다.
