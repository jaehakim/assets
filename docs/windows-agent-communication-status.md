# Agent 0.2.11 통신 상태와 로그

## 트레이 상태

| 색상 | 의미 | 판정 |
|---|---|---|
| 초록 / 체크 | 서버 통신 정상 | 최근 12분 이내 성공, 미해결 작업 오류 없음 |
| 빨강 / 느낌표 | 통신 또는 작업 오류 | 등록·하트비트·인벤토리·업데이트 중 실패가 남음 |
| 노랑 / 느낌표 | 통신 확인 지연 | 서비스는 동작하나 성공한 통신이 12분 넘게 없음 |
| 회색 / 대시 | 초기 대기·서비스 응답 없음 | 상태 파일 없음/읽기 실패, 첫 통신 전, 서비스 상태 갱신이 45초 넘게 중단 |

서비스가 10초마다 공개 상태 파일을 기록하고 트레이가 5초마다 읽는다. 변경 반영은 정상 스케줄링 시 최대 약 15초, 서비스 강제 종료 감지는 약 45~50초다. 요청 실패는 HTTP 오류 또는 시간 초과가 확정된 시점에 반영된다. 현재 HTTP 제한 시간은 최대 5분으로, 네트워크 단절 직후 즉시 빨강을 보장하지 않는다.

우선순위: 상태 파일 없음/서비스 응답 없음 → 미해결 오류 → 첫 통신 대기 → 장기 통신 지연 → 정상. 서버에 별도 주기 요청을 추가하지 않고 실제 등록·하트비트·인벤토리·업데이트 작업 결과를 사용한다. 초록은 최근 통신 성공을 뜻하며 지속 연결을 뜻하지 않는다.

작업별 실패는 해당 작업의 다음 성공 시 해제한다. 예: 인벤토리 실패 후 하트비트만 성공해도 빨강 유지. 인벤토리 재시도 간격이 60분이면 오류 해제까지 다음 성공을 기다릴 수 있다. 우클릭 메뉴에서 실패 작업·마지막 통신 시각·상태 문구를 확인한다.

상태 파일: `%ProgramFiles%\AssetFlow\Agent\agent-status.json`. 토큰·사용자 인벤토리 본문을 포함하지 않으며 서비스가 임시 파일 작성 후 교체한다. 트레이 읽기는 파일 교체를 방해하지 않도록 공유 삭제 접근을 사용한다. 쓰기 권한은 정상적인 Program Files 설치 ACL에 의존한다. 임의 설치 경로나 변조된 ACL에 대한 강화는 별도 삭제 방지 계획 대상이다.

## 통신 이력

- 위치: `%ProgramData%\AssetFlow\logs\communication-YYYYMMDD.log`.
- 서비스·작업 결과와 상태 전이: 같은 폴더의 `agent-YYYYMMDD.log`.
- 트레이 예외: `%LOCALAPPDATA%\AssetFlow\logs\tray-YYYYMMDD.log`.
- 우클릭 메뉴의 `서비스·통신 로그 열기`로 폴더를 연다.
- 0.2.10 이전 로그는 기존 `%ProgramFiles%\AssetFlow\Agent\logs`에 남으며 자동 이관하지 않는다.

| 이벤트 | 기록 항목 |
|---|---|
| `HTTP_START` | 타임존 포함 시각, 요청 ID, HTTP 메서드, 정규화된 API 경로, 알려진 요청 Content-Length |
| `HTTP_RESPONSE` | 같은 요청 ID, HTTP 코드, 성공/실패, 응답 헤더까지 소요 시간(ms), 알려진 응답 Content-Length |
| `HTTP_FAILED` | 요청 ID, 네트워크 예외 종류 또는 CANCELLED_OR_TIMEOUT, 소요 시간 |
| `INVENTORY_ACK` | 서버가 수락한 전송의 디스크·소프트웨어 항목 수 |
| `DOWNLOAD_COMPLETE` | 다운로드 스트림 완료 시 버전과 실제 기록 바이트 |
| 서비스 작업 완료/실패 | 등록·하트비트·인벤토리·업데이트 전체 작업 결과와 실패 예외 |
| `TRAY_STATUS` | 서비스가 판정한 상태 변화, 색상 및 설명 |

Content-Length가 없는 스트리밍/청크 요청은 크기가 비어 있을 수 있다. 응답 헤더 성공 이후 본문 수신·파싱·파일 저장·해시 검증에 실패할 수 있으므로 `HTTP_RESPONSE SUCCESS`만으로 전체 작업 성공을 판정하지 않는다. `DOWNLOAD_COMPLETE`도 해시 검증 완료 전 이벤트이며 전체 업데이트 결과는 서비스 로그에서 확인한다.

HTTP 타임아웃과 서비스 종료 취소는 전송 핸들러에서 `CANCELLED_OR_TIMEOUT`으로 기록한다. 서비스 종료 요청은 작업 오류로 반영하지 않는다. 실패 작업은 기존 정책에 따라 재시도한다.

통신 로그에는 Authorization·등록 토큰·쿠키·URL 쿼리·서버 호스트·요청/응답 본문·장비명·설치 소프트웨어명을 기록하지 않는다. API 경로도 등록/heartbeat/inventory/latest/download 등의 고정 값으로 정규화한다.

서비스 로그와 통신 로그는 파일별 10MiB 기준 분할, 유형별 하루 현재 파일+이전 4개, 최근 30일 보관이다. 기준을 넘긴 다음 쓰기 전에 분할하며 큰 한 줄 때문에 파일 크기가 기준을 넘을 수 있다. 오래된 로그 정리는 하루 첫 기록 시 실행한다. 트레이 진단 로그는 기존 정책을 유지한다. 디스크 공간·권한 문제로 로그를 못 쓰더라도 통신을 중단하지 않는다.

로그는 로컬 파일이며 중앙 서버로 자동 전송하지 않는다. 기본 재설치 시 ProgramData 로그는 보존되지만 명시적 `/purge` 제거 시 함께 삭제된다.

## 검증

`docker run --rm -v "$PWD:/src" -w /src mcr.microsoft.com/dotnet/sdk:8.0 dotnet run --project agent-tests/AgentHealth.Tests.csproj -c Release`

자동 시험: 초기 대기, 등록 오류/복구, 작업별 오류 유지, 성공 복구, 서비스 중단, 통신 지연, 시계 역행, JSON 전달, 동시 상태 변경, HTTP 200/204/401/500, 네트워크·취소 예외, 비밀정보 비노출, 로그 보관·분할·쓰기 실패 격리.

Windows 실기 시험: Windows 10·11 x64에서 정상 통신, 서버 차단/복구, 잘못된 토큰, 인벤토리 오류, 서비스 중지/시작 후 색상과 두 로그를 대조한다. 숨김 아이콘 영역도 확인한다. Linux 교차 빌드 환경에서는 실제 Windows 화면을 시험하지 못했다.
