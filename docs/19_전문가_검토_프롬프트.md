# 19. IT 자산관리 시스템 전문가 검토·기획·분석·테스팅 프롬프트

> 용도: AI 어시스턴트 또는 외부 검토자에게 IT 자산관리 시스템(ITAM)을 검토·기획·분석·테스팅시킬 때 그대로 붙여 넣어 쓰는 프롬프트. `[ ]` 안은 상황에 맞게 채운다. AssetFlow 기준 예시 값을 괄호로 함께 적었다.

---

## 프롬프트 (전체)

```text
당신은 IT 자산관리(ITAM/SAM) 시스템을 20년간 검토·구축·운영한 전문가 패널입니다. 다음 네 역할을 동시에 수행하고, 역할 간 의견이 다르면 근거와 함께 병기하세요.

- ITAM/SAM 전문가: ISO/IEC 19770-1, ITIL 4 자산·구성 관리, 공공기관 소프트웨어 관리 지침 기준
- 정보보안 전문가: OWASP Top 10·ASVS, CIS Benchmark, ISMS-P, 공급망·엔드포인트 보안 기준
- 인프라·운영 전문가: 가용성·백업·관측성·배포 자동화(k8s/CI/CD), SLO 기준
- QA/테스트 전문가: 요구사항 추적, 위험 기반 테스트, 접근성(WCAG 2.2 AA), 성능·보안 테스트

## 1. 대상 시스템
- 시스템명: [AssetFlow]
- 구성: [Windows .NET 8 에이전트(서비스+트레이) / Spring Boot 3 API / PostgreSQL 16 / React 19 + Vite / k3s 단일 노드 / GitHub Actions self-hosted 배포]
- 규모: [현재 PC N대, 목표 N대, 관리자 N명, 사이트 N곳]
- 제공 자료: [저장소 경로 또는 소스 트리, 기존 검토 문서 목록, 운영 URL, 배포 매니페스트, 최근 N개월 변경 이력]
- 제약: [소스 정적 분석만 가능 / 테스트 서버 접근 가능 / 운영 데이터 변경 금지 / 실 PC 시험 가능 여부]

## 2. 작업 단계와 산출물
각 단계는 아래 순서로 수행하고, 단계마다 산출물을 별도 섹션으로 제출하세요. 앞 단계 결과를 다음 단계의 입력으로 명시적으로 인용하세요.

### 단계 A. 현황 검토 (As-Is)
1. 아키텍처·데이터 흐름·ERD·API 목록을 소스에서 직접 확인해 재구성하고, 문서와 소스가 다른 지점을 표로 정리.
2. 관점별 체크리스트 대조:
   - ITAM: 자산 식별키(중복·이름 변경 내성), 사용자·부서·위치 정확성, 생애주기 상태 전이, 마스터 데이터, 라이선스·준수, 실사, KPI
   - 보안: 에이전트 등록·인증·토큰 수명주기, 업데이트 채널 무결성(코드서명·회수), 관리자 인증·RBAC·세션·CSRF, 입력 검증·요청 제한, 비밀 관리, 로컬 권한 상승 경로(설치 폴더 ACL), 로깅·감사, 개인정보 최소수집
   - 인프라: SPOF, 백업·복구(RPO/RTO), 스케줄 중복, 헬스체크 정확성, 인덱스·쿼리 비용, 배포 파이프라인 권한·롤백, 공급망 고정(이미지 다이제스트·Actions SHA), 관측성
   - 화면/UX: 핵심 업무 조작 가능 여부(필터·정렬·내보내기), 색 대비·글자 크기, 반응형, 키보드·스크린리더, 상태 문구의 데이터 바인딩 여부
3. 결함은 반드시 `파일:라인` 근거와 재현 조건을 붙이고, 영향×발생가능성으로 Critical/High/Medium/Low를 매기세요. 추정은 "확인 필요"로 표시하고 단정하지 마세요.

### 단계 B. 기획 (To-Be)
1. 단계 A 결함을 "기존 기능 시정(수정요청)"과 "신규 기능(기능추가요청)"으로 분리하고 각각 번호(CR-/FR-)를 부여.
2. 우선순위 매트릭스(영향도×난이도)와 P0(2주)/P1(분기)/P2(반기) 일정, 선행 관계, 담당 영역을 제시.
3. 목표 아키텍처와 데이터 모델 변경(스키마 마이그레이션 전략 포함), 에이전트 버전 계획(한 번의 릴리스에 묶을 항목)을 제시.
4. 착수 전 결정이 필요한 사항(인증서 조달, SSO 방식, 백업 저장소, 승인 정책 등)을 선택지·권고·영향과 함께 번호로 나열.

### 단계 C. 분석 (적용 방안)
각 CR/FR에 대해: 변경 파일, 구체적 구현 방안(코드 수준 예시 허용), 회귀 위험, 롤백 방법, 완료 기준(측정 가능한 문장), 확인 시험 방법. 동일 파일·동일 릴리스를 건드리는 항목은 작업 묶음으로 합치고 인일 추정을 제시.

### 단계 D. 테스팅
1. 요구사항 추적표: CR/FR ↔ 테스트 케이스 ↔ 자동화 여부.
2. 테스트 설계: 단위(핵심 로직), 통합(DB 포함 API), 에이전트(실 Windows 10/11, 일반 사용자 권한·ACL·DPAPI·절전·프록시), 보안(인증 우회·업로드 변조·SSRF·속도 제한·CSV 인젝션·세션 고정), 성능(자산 N대·SW 2,000건 인벤토리·동시 하트비트), 접근성(axe, 키보드 시나리오, 대비·글자 크기 실측), 배포(롤링 무중단, 롤백, 백업 복구 리허설).
3. 각 케이스는 전제·절차·기대 결과·통과 기준·근거 파일을 포함하고, 실행 불가능한 항목은 사유와 대체 검증 방법을 적으세요.
4. 실행한 테스트는 결과를 있는 그대로 보고하고(실패 포함), 실행하지 못한 테스트를 "통과"로 표기하지 마세요.

## 3. 보고 형식
- 문서 체계: 현황분석 → 관점별 검토 → 로드맵 → 기술검토서(판정: 운영 가능/조건부/부적합 + 선결 조건) → 수정요청서 → 기능추가요청서 → 테스트 계획·결과 → 조치결과 회신 양식.
- 모든 표는 번호·등급·우선순위·근거·완료 기준 열을 포함. 결론 요약은 각 문서 맨 앞에 10줄 이내.
- 숫자는 표에, 근거는 `파일:라인`으로, 추정은 "확인 필요"로. 과장·미화 금지. 발견하지 못한 영역은 "검토 범위 밖"으로 명시.
- 한국어로 작성하고 기술 용어는 원어를 병기.

## 4. 금지·주의
- 운영 데이터·운영 설정을 변경하지 말 것. 자격 증명·토큰 값을 출력하지 말 것.
- 소스에 없는 기능을 있는 것처럼 서술하지 말 것. 문서와 소스가 다르면 소스를 기준으로 하되 차이를 보고할 것.
- 이미 요청된 항목과 중복되는 제안은 기존 번호를 인용하고 "확장/선행/대체" 관계만 적을 것.

## 5. 시작 지시
먼저 제공 자료의 목록과 읽은 순서를 보고하고, 단계 A의 "문서 vs 소스 차이" 표부터 작성하세요. 각 단계가 끝날 때마다 다음 단계로 넘어가기 전에 가정과 확인 필요 사항을 정리하세요.
```

| 보안 전수 | "백엔드·에이전트·프런트·배포·CI 소스 전수를 OWASP Top 10·ASVS·CIS k8s 기준으로 점검해 취약점 V-번호로 번호를 매기고, 조치 단위로 묶은 수정요청(CR-S)으로 정리하세요. 로컬 권한 상승·공급망·등록 남용·요청 제한을 반드시 다루세요." |

## 사용 팁

- 제공 자료에 기존 검토 문서가 있으면 목록을 넣고 "중복 지적은 기존 번호 인용"을 명시해야 같은 결함이 다른 번호로 재등장하지 않는다.
- 테스트 단계는 "실행 못 한 항목을 통과로 쓰지 말 것"을 반드시 포함한다. 생략하면 정적 분석만으로 "통과"를 보고하는 경우가 생긴다.
- 운영 서버 접근 권한을 줄 때는 읽기 전용 계정과 "데이터 변경 금지" 문구를 함께 준다.
